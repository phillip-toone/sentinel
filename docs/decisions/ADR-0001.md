# ADR-0001 - Adopt an Architecture-First Development Process

## Status

Accepted

---

## Context

Sentinel is intended to be a long-lived engineering project whose primary goal is to produce a reliable, maintainable, and reusable fencing scoring platform.

Many software projects begin implementation immediately, allowing architecture to emerge over time. While this approach can be effective for prototypes, it often leads to unnecessary complexity, tightly coupled components, and documentation that lags behind the implementation.

Because Sentinel aims to separate fencing rules from hardware, communication protocols, and user interfaces, the architecture of the system is considered one of the project's most valuable assets.

The project also has an educational goal: to demonstrate thoughtful software engineering practices for embedded systems.

Sentinel is not intended to validate previous implementations. It is an opportunity to reconsider every architectural decision from first principles, retaining only those ideas that continue to represent the best available solution.

---

## Decision

Sentinel will adopt an architecture-first development process.

Before implementing production firmware, the project will establish:

- Project vision
- Requirements
- Architectural specifications
- Major subsystem responsibilities
- Communication interfaces
- Research findings
- Architecture Decision Records (ADRs)

Implementation should follow the architecture rather than define it.

Whenever practical, important architectural decisions will be documented before they are implemented.

---

## Rationale

This approach provides several advantages.

### Improved Maintainability

A well-defined architecture makes the project easier to understand, modify, and extend.

### Better Testability

Separating architecture from implementation encourages modular components that can be tested independently.

### Reduced Coupling

Clearly defined responsibilities reduce dependencies between hardware, firmware, and user interfaces.

### Easier Collaboration

Future contributors can understand the project's design without reverse engineering the implementation.

### Educational Value

One of Sentinel's goals is to demonstrate modern embedded software engineering practices.

Documenting design decisions is part of that objective.

---

## Consequences

### Positive

- Better organized project.
- Clear separation of responsibilities.
- Easier onboarding for future contributors.
- Improved long-term maintainability.
- Architecture remains independent of hardware choices.
- Supports development of a portable scoring engine.

### Negative

- Slower initial progress.
- Additional effort spent on documentation.
- Some architectural decisions may require revision as implementation progresses.

These tradeoffs are considered acceptable because the project prioritizes long-term quality over short-term implementation speed.

---

## Alternatives Considered

### Implementation-First Development

Begin writing firmware immediately and allow the architecture to evolve over time.

Rejected because this approach often results in architectural decisions being driven by implementation details rather than system requirements.

### Prototype First, Architecture Later

Build a working prototype before documenting the architecture.

Rejected because Sentinel is not intended to be an experimental proof of concept. The project emphasizes correctness, maintainability, and reuse from the beginning.

---

## Future Revisions

This decision establishes the development philosophy of the project.

It is expected to remain valid throughout the lifetime of Sentinel, although the specific processes used to implement this philosophy may evolve.
